## 1. 修复的问题

历史 `scripts/run_queue_0918.py` 只检查本队列成员的输出目录，无法发现另一队列正在训练。
后续三个脚本虽然增加了全系统 `train_peft.py` 查询，但仍有四个共同缺陷：

1. 每个脚本复制一份不同实现，容易再次漂移；
2. “检查无人训练”与“启动训练”之间没有原子互斥，两个队列可能同时穿透；
3. CIM 查询异常时按“假定无人训练”继续，失败方向不安全；
4. 已存在但没有 `metrics.json` 的半成品目录可能导致无限等待，无法区分活跃训练与异常遗留。

B07 将四个历史队列全部切换到同一共享守卫，旧的局部检查、轮询和复制的 PowerShell 查询已移除。

## 2. 新的互斥模型

共享实现位于 `src/aictrack1/engine/training_queue.py`。

每个训练项按以下顺序处理：

1. 检查输出目录：不存在才可启动；完整产物可跳过；半成品硬停止；
2. 以 `O_CREAT | O_EXCL` 原子创建 `artifacts/queues/training.lock.json`；
3. 在持锁状态下查询系统内所有受管训练入口；
4. 仅当查询成功且没有训练进程时启动唯一子进程；
5. 子进程 PID 写回锁记录；
6. 等待子进程退出，校验返回码和完整输出，再释放锁并考虑下一项。

锁记录包含 schema、随机 token、队列 owner、队列 PID、trainer PID、config、输出目录、开始时间
和完整命令。另一队列只能看到锁并停机，不能覆盖或删除。

受管进程入口当前包括 `train_peft.py`、`train_frozen_head.py` 和 `train_final_h1_lora.py`。

真实主机上的只读 CIM 探测已验证可运行，当前返回空列表。受限沙箱中 CIM 返回“拒绝访问”时，
守卫会按设计抛出错误并阻止启动，证明失败方向为 fail-closed。

## 3. 输出目录与异常语义

一个运行只有同时存在以下文件才被队列视为可跳过的完整结果：

- 可解析的 `metrics.json`；
- metrics 指向的安全 basename checkpoint；
- 对应 checkpoint 文件；
- `config.yaml`；
- `command.txt`。

目录为空、缺 metrics、metrics 损坏、checkpoint 缺失或路径越出仓库，都属于半成品并停机。

如果子进程正常返回非零，队列释放自己仍明确持有的锁、记录失败并停止，不启动下一项。如果 launcher
已经记录 trainer PID，但队列无法确认子进程是否退出，则锁被有意保留；人工必须先确认进程状态，
再按 token 清理，避免“队列挂了但训练仍在跑”时误启第二项。

## 4. 残留锁操作

新增 `scripts/manage_training_lock.py`：

```powershell
.\.venv\Scripts\python.exe scripts\manage_training_lock.py status
.\.venv\Scripts\python.exe scripts\manage_training_lock.py clear `
  --confirm-stale-token <status输出的完整token>
```

`clear` 同时要求：锁仍是同一 token、队列 owner PID 已不存在，且全系统进程探测成功并确认没有
受管训练。错误 token、owner 仍在、仍有训练、锁在检查期间变化或进程查询失败都会拒绝删除。
队列本身没有自动清理陈旧锁的代码。

## 7. 边界

- 原子文件锁约束同一仓库；同机另一份 clone 由全系统进程探测兜底。
- 无法读取系统进程时队列不能自动启动，需要先解决权限问题，不能通过关闭探测绕过。
- 手工直接运行训练入口不会主动获取队列锁，但队列会检测其进程并拒绝并发。正式训练仍应优先使用
  任务单规定的统一队列或由操作者确保单进程。
- 本批未实际启动训练，因此只验证互斥控制流，不验证 GPU 占用或长时运行稳定性。
