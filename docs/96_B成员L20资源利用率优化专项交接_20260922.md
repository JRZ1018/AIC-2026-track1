## 1. 任务结论先行

我们在阿里云单卡 NVIDIA L20 上运行 Stage 2 last-4 PEFT 时，GPU 没有持续获得足够工作：

- 两轮连续 180 秒、每秒一次的采样中，GPU SM 平均利用率只有约 **15.4%** 和 **10.13%**；
- SM 利用率中位数为 **0%**，SM 为 0 的采样比例分别约 **63.33%** 和 **69.44%**；
- 显存仅使用约 **1.7/46.1 GiB**，不是显存容量瓶颈；
- 整机 32 vCPU 的活跃率约 **12.5%–13.4%**，I/O wait 接近 0；
- 训练主进程只占少量 CPU，4 个 DataLoader worker 通常各占满一个核，其余 CPU 大量空闲；
- L20 训练循环平均约 **369.72 samples/s**，本机 RTX 4060 Laptop 的历史同类训练约
  **364.08 samples/s**，实测只有约 **1.02 倍**，远低于硬件理论差距；
- 固定验证运行的端到端 epoch 还比本机历史运行更慢，但两者验证开销和数据规模不同，因此不能把
  该端到端差值直接解释为 GPU 性能差。

当前最可信的判断是：CUDA 路径本身正常，GPU 能在短时突发中达到 90%–100%，但 batch 之间存在
明显供给或同步空档。优先怀疑 DataLoader 并行度与生命周期、逐 batch CPU/GPU 同步、图片解码与
变换开销；“L20 算力不足”不是当前证据支持的结论。

本专项的目标是降低训练墙钟时间和租金成本，不是单纯把 `nvidia-smi` 数字做高，也不是修改模型
来制造更高利用率。

## 3. 已定位的代码热点

### 3.1 DataLoader 配置过于保守

`scripts/train_peft.py` 的 `_loader()` 当前只有 `num_workers`、`pin_memory` 和
`persistent_workers`；没有可配置的 `prefetch_factor`。正式配置固定为 workers=4，而远端有 32 vCPU。

重点位置：

- `scripts/train_peft.py:107`：`_loader()`
- `scripts/train_peft.py:130`：构造 `DataLoader`
- `scripts/train_peft.py:136`：`num_workers=workers`
- `scripts/train_peft.py:138`：`persistent_workers=workers > 0`

### 3.2 `persistent_workers=True` 实际没有跨 epoch 复用

训练循环在每个 epoch 内重新调用 `_loader()`：

- `scripts/train_peft.py:550`：epoch 循环
- `scripts/train_peft.py:555`：每轮重新构造训练 DataLoader

因此上一轮 DataLoader 被销毁，新一轮重新创建 worker。采样时观察到 epoch 边界旧、新 worker 的
退出/启动空档。真正把 DataLoader 移出 epoch 循环后，还必须解决 `IndexedImageDataset.set_epoch()`
对持久 worker 的可见性，否则随机增强会使用旧 epoch，破坏确定性。

相关位置：

- `src/aictrack1/data/indexed_images.py:168`：`set_epoch()` 只修改主进程对象字段
- `src/aictrack1/data/indexed_images.py:190`：随机种子依赖 epoch 与 sample index

### 3.3 每个 batch 有多次强制 CUDA 同步

训练循环每 batch 执行：

- `float(loss.detach())`
- `labels.detach().cpu()`
- sample index、逐样本 loss、概率、预测结果 `.cpu()`

重点位置为 `scripts/train_peft.py:609-622`。这些操作可能使 GPU 等待 CPU 回收结果，尤其 AC 开启时
同步次数更多。优化时应在 GPU 侧累计，到 epoch 结束再批量同步，但必须保持 AC 状态、采样计数、
checkpoint resume 和指标完全等价。

### 3.4 图片解码与变换存在重复工作

- `src/aictrack1/data/indexed_images.py:181-182`：打开图片后立即 `convert("RGB")`
- `src/aictrack1/data/transforms.py:66`：transform 再次 `convert("RGB")`
- `src/aictrack1/data/transforms.py:33`：`_normalize()` 第三次请求 RGB 转换
- `src/aictrack1/data/transforms.py:35-36`：每张图片重新构造 mean/std Tensor

这些是可验证的 CPU 开销候选，但不能在没有基准的情况下直接大改解码栈。

### 3.5 环境记录曾有 cuDNN 冲突

远端训练结束时曾出现 PyTorch 自带 cuDNN 与系统动态库版本不一致，导致环境身份采集失败；训练主体和
checkpoint 未损坏。代码已改为如实记录探测错误，不再让 metadata 收尾破坏完整训练。B 的环境基线
必须记录 PyTorch、CUDA、cuDNN、驱动和动态库来源，不能只验证 `torch.cuda.is_available()`。

## 5. 执行计划

### P0：冻结基线与建立可重复 profiler（20–45 分钟开发，20–30 分钟 L20 运行）

1. 新增 train-only 运行时基准入口，使用真实 Stage 2 train manifest，但不读取 test。
2. 固定 warmup 和计时窗口，例如 100 step warmup + 400 step 计时；所有候选使用同一顺序、seed、batch。
3. 每个配置至少重复两次；第一次允许文件缓存预热，报告冷/热两组结果。
4. 记录：data wait、host-to-device、forward、backward、optimizer、AC bookkeeping、epoch/窗口 wall time。
5. 使用 `torch.profiler` 或 CUDA event 采集 200–500 step 的短窗口；profiler 输出进入 `artifacts/`，
   只把轻量摘要提交 Git。
6. 同时采集 `nvidia-smi dmon`、`pidstat`、`vmstat`；记录实例单价以计算每百万样本成本。

P0 先回答“空闲发生在哪里”。没有 P0 基线，不进入大范围重构。

### P1：workers 与 prefetch 单变量扫描（约 1–1.5 小时）

保持模型、batch、seed、样本顺序和算法完全不变：

| ID | workers | prefetch_factor | 唯一变化 |
|---|---:|---:|---|
| W0 | 4 | 2 | 当前基线 |
| W1 | 8 | 2 | workers |
| W2 | 12 | 2 | workers |
| W3 | 16 | 2 | workers |
| P1 | 最优 workers | 4 | prefetch |
| P2 | 最优 workers | 8 | prefetch |

`prefetch_factor` 仅在 workers>0 时传给 DataLoader。连续两档吞吐提升均小于 5%，或 CPU/内存压力
明显增加时停止扩张。不要同时改 batch size。

### P2：减少逐 batch CUDA 同步（1–2 小时开发与回归）

1. 在 GPU 上累计 loss、类别计数、逐样本 loss、观测概率和预测。
2. epoch 结束时一次性回传 CPU，或采用容量明确的预分配 buffer；避免每 batch 小 tensor `.cpu()`。
3. 保留非有限 loss 安全门禁。若减少每 batch 检查，必须用测试证明 NaN/Inf 能及时停止且不会保存坏状态。
4. 计时区间前后显式 `torch.cuda.synchronize()`，防止异步 kernel 让计时虚低。
5. 对比优化前后：train loss、采样计数、AC diagnostics、下一 epoch 权重、checkpoint 状态必须一致。

P2 建议独立 commit，便于在无收益或语义风险时整块回退。

### P3：真正复用 DataLoader worker（2–4 小时，风险最高）

1. 将训练 DataLoader 生命周期移到 epoch 循环外。
2. 设计 worker 可见的 epoch 状态，不能只修改主进程 dataset 实例。
3. 证明增强随机数仍由 `(stochastic_seed, epoch, sample_index)` 唯一决定。
4. 分别覆盖自然采样、WeightedRandomSampler、workers=0、workers>0、断点续训。
5. 验证 epoch 边界不再重启 worker，也没有跨 epoch 预取污染。

如果不能证明确定性与断点恢复一致，P3 不合并；workers/prefetch 和 P2 仍可独立保留。

### P4：图片解码与变换低风险优化（2–4 小时）

按顺序逐项测试：

1. 删除重复 RGB 转换，但保留 EXIF 容错语义；
2. 预构造并复用 CLIP mean/std Tensor；
3. 基准 Pillow/libjpeg-turbo 与 torchvision v2；
4. 只有 profiler 仍显示解码瓶颈时，才评估 nvJPEG/DALI 或 train-only 缓存。

任何解码替换都要随机抽样比较图像尺寸、dtype、数值范围、归一化和确定性增强。引入 DALI 等新依赖
会显著扩大环境复杂度，不是默认方案。

### P5：batch size 和并发实验（后置、非等价优化）

只有 P1–P4 完成后才测试 batch 128/256。batch size 会改变优化动力学，必须重新验证 Top-1、macro、
tail、零召回类和有效质量，不能只看吞吐。多实验并发只在有多个独立候选时评估，总吞吐与单位成本是
指标；最终单模型训练仍优先保持单任务。

## 6. 测试与验收门槛

### 6.1 必须新增或强化的回归测试

- workers/prefetch 配置解析与非法组合；
- workers=0 与 workers>0 的 DataLoader 行为；
- 同 seed、同 epoch、同 sample index 的增强完全一致；
- epoch 改变时增强按预期改变；
- persistent worker 下 epoch 状态可见；
- 自然采样与 WeightedRandomSampler 的样本数和顺序契约；
- AC 更新前后逐样本 loss、probability、prediction 与权重等价；
- NaN/Inf 停止门禁；
- checkpoint 保存、恢复和下一 epoch 顺序一致；
- CPU 小样本 smoke 与 CUDA 短 smoke。

完整回归至少运行：

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe scripts\check_governance.py
```

Linux/L20 使用对应虚拟环境解释器，命令语义相同。

### 6.2 性能晋级标准

主要标准：

1. 同输入、同算法下训练吞吐达到当前基线的 **>=1.5x**；低于 1.2x 时一般不值得增加正式管线复杂度。
2. 完整 epoch 训练墙钟至少下降 **30%**。
3. GPU SM 平均目标 **>=40%**，SM 为 0 的比例目标 **<30%**；GPU 指标只作诊断。
4. 相同训练输入下，训练样本数、顺序、loss、AC 状态和 checkpoint provenance 可复核。
5. 完整验证的 Top-1、macro、tail、有效质量和零召回类不得出现超出数值容差的变化。
6. 报告每百万训练样本成本、单 epoch 成本和相对本机 4060 的实测加速比。

如果最终单任务吞吐仍低于本机 4060 的 1.5x，应建议停止为单任务租用 L20；L20 只保留给受控并发
或确有显存需求的任务。
