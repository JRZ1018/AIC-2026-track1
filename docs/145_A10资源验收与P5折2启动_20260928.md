## 3. 判定与优化

workers 4→8 没有提高 GPU 平均利用率，反而把 CPU idle 从 45.79% 压到 3.16%，说明简单增加 loader worker 已触顶。单任务显存低并不等于应放大单模型 batch；改变有效 batch 会改变优化轨迹和分数风险。

采用仓库已有的受控双任务并行：两个冻结候选各自保持 batch64、workers4、损失、LR、seed、split、H1、增强和 AC 不变，独立输出/日志/checkpoint，由同一个原子训练锁管理。aggregate GPU P50 提升到 94%，同时计算两份候选；最终仍只选择一个单模型、单 checkpoint，不融合、不投票。

未采用的后续项：workers>8、扩大单模型 batch、运行中修改训练源码。CPU 已接近饱和，继续堆 worker 预期只会加剧争用；正式批次冻结后也禁止修改活跃源码。

## 4. 失败与恢复记录

- 首个 1ep profile 因 `warmup_epochs=1` 不满足 `warmup_epochs < epochs` 在占用 GPU 前退出，保留日志，未用其评价资源。
- workers=4 v2 和 workers=8 profile 在采样后按精确训练锁 PID 终止。workers=8 终止后留下两个同配置、PPID=1 的 DataLoader 孤儿；逐 PID/命令核验后终止，GPU 上下文归零。正式队列首次正确拒绝在孤儿存在时启动。
- 本机全量队列测试受已有 Windows 临时目录权限问题影响；Linux 运行 21 项时 19 项通过，2 项失败为 Windows 探针测试在 Linux 下模拟输出。与本次直接相关的 parallel queue 用例 2/2 通过。
