# 双人协作与训练执行交接手册

更新时间：2026-09-11（Asia/Shanghai）

## 1. 目的与角色定义

本手册用于两台电脑、两名工作人员长期并行推进本赛题。协作模式不是两人同时自由修改同一套代码，而是：

- **A：核心研发与决策负责人**。负责算法、代码、配置、实验设计、结果判断、Git 集成、模型锁定、测试推理和正式提交。
- **B：训练执行与算力负责人**。使用第二台电脑，严格执行 A 已冻结的训练任务单，负责长训练、多随机种子、固定消融、日志和产物回传；不自主改代码、依赖、配置或实验路线。

三个同步通道必须分开：

| 内容 | 唯一同步方式 | 禁止事项 |
|---|---|---|
| 源码、配置、测试、文档、轻量实验记录 | GitHub | 不用 U 盘覆盖整个仓库，不复制 `.git/` |
| 初赛官方数据 | 两台电脑分别从比赛官方渠道获取 | 不上传 GitHub，不从非官方来源获取 |
| 权重、checkpoint、特征缓存、审计派生产物、真实提交包 | U 盘或仅团队可访问的私有存储，并校验 SHA-256 | 不进入公开 GitHub、GitHub Release 或公共网盘 |

详细竞赛边界仍以 `AGENTS.md` 和正式赛题规则为准；本手册只增加协作约束，不放宽任何合规要求。

## 2. 新电脑首次同步

### 2.1 前置条件

新电脑建议准备：

- Windows 10/11；
- Git；
- 64 位 Python 3.12 和 `py` 启动器；
- NVIDIA GPU 及可用驱动；
- 至少 40 GiB 可用磁盘空间，用于官方数据、Python 环境和后续训练产物；
- 可访问 GitHub、PyPI、PyTorch 官方轮子索引和比赛官方下载渠道的网络。

B 不需要取得 A 的 GitHub 密码、访问令牌或 SSH 私钥。若 B 仅执行训练，公开仓库可直接只读克隆；只有确需推送轻量记录时，才由仓库所有者将 B 的独立 GitHub 账号添加为 Collaborator。

### 2.2 A 在当前电脑制作私有初始化包

私有包默认不包含 `DataSetStage1/`，包含当前官方 CLIP 权重、固定审计与划分、A1/M1 checkpoint、首份真实提交备份和可选冻结特征缓存。假设 U 盘盘符为 `E:`：

```powershell
Set-Location D:\aicomp\AICtrack1
git status --short --branch
D:\aicomp\python312\python.exe scripts\transfer_workspace.py plan --include-features
D:\aicomp\python312\python.exe scripts\transfer_workspace.py create E:\AICtrack1-bootstrap-20260911 --include-features
D:\aicomp\python312\python.exe scripts\transfer_workspace.py verify E:\AICtrack1-bootstrap-20260911
```

目标目录必须为空。默认含特征缓存的私有包约 0.49 GiB。更完整的迁移边界见 `docs/16_换机迁移与恢复指南.md`。

### 2.3 B 从 GitHub 克隆，而不是复制 A 的仓库

```powershell
git clone https://github.com/JRZ1018/AIC-2026-track1.git D:\aicomp\AICtrack1
Set-Location D:\aicomp\AICtrack1
git status --short --branch
```

预期为干净的 `main`。不要把 A 电脑的整个 `AICtrack1/` 或 `.git/` 复制到 B 电脑。

### 2.4 B 恢复私有初始化包

迁移脚本只使用 Python 标准库，可以在创建项目虚拟环境前运行：

```powershell
Set-Location D:\aicomp\AICtrack1
py -3.12 scripts\transfer_workspace.py verify E:\AICtrack1-bootstrap-20260911
py -3.12 scripts\transfer_workspace.py restore E:\AICtrack1-bootstrap-20260911
```

该包包含灾难恢复所需的历史测试 manifest 和首份提交备份。B 不得打开、统计或利用测试预测；测试相关文件只由 A 用于最终推理、格式校验和提交。

### 2.5 B 从官方渠道取得数据

B 从比赛官方渠道重新下载同阶段数据，解压后的唯一入口必须是：

```text
D:\aicomp\AICtrack1\DataSetStage1\train
D:\aicomp\AICtrack1\DataSetStage1\test
```

初赛已知基准数量为训练 103,218 张、测试 24,967 张、500 类。若数量、目录结构或官方版本与这些基准不一致，B 停止训练并通知 A，不自行重建类别映射或固定划分。

### 2.6 B 创建独立 Python 环境

```powershell
Set-Location D:\aicomp\AICtrack1
powershell -ExecutionPolicy Bypass -File scripts\setup_environment.ps1
```

之后一律使用仓库内解释器：

```powershell
.\.venv\Scripts\python.exe
```

不要复制 A 的 `D:\aicomp\python312`、`.venv/`、pip 缓存或 CUDA Toolkit。不要自行升级 torch、torchvision、CLIP 或其他依赖。

### 2.7 B 完成首次验收

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe scripts\check_governance.py
powershell -ExecutionPolicy Bypass -File scripts\check_environment.ps1 -PythonExecutable .\.venv\Scripts\python.exe
.\.venv\Scripts\python.exe scripts\manage_upstream_references.py sync
.\.venv\Scripts\python.exe scripts\manage_upstream_references.py check
git status --short --branch
```

验收标准：

- 测试和治理检查全部通过；
- `torch.cuda.is_available() == True`，GPU 型号和显存已记录；
- 官方 CLIP 权重及关键 checkpoint 哈希通过；
- 上游仓库均位于注册表锁定 commit；
- Git 工作区干净，数据、权重、缓存、checkpoint 和提交包没有进入候选文件；
- A 留存 B 的首次环境输出。

首次环境验收完成前，B 不运行正式训练。

## 3. 两人分工方案

### 3.1 A 的职责与权限

A 独占以下工作：

- 赛题理解、合规判断和技术路线；
- 核心算法、训练器、数据管线、损失函数和 checkpoint 代码；
- 所有正式配置、随机种子和实验预算设计；
- 新方法的单元测试、smoke test 和异常调试；
- 是否启动、停止、续跑、复训或回退的决策；
- 验证集诊断、消融解释和最终选模；
- `main` 分支集成、版本标签、实验总台账和提交台账；
- 测试集推理、`pred_results.csv`、ZIP 和线上提交；
- 技术报告核心结论。

A 的电脑优先运行研发性、短周期、高信息密度或需要边调试边观察的任务。

### 3.2 B 的职责与权限

B 只执行 A 已冻结的任务单，包括：

- 多随机种子重复训练；
- 已确定范围的单变量消融；
- 正式长训练与安全续跑；
- 冻结训练特征提取；
- 已指定 checkpoint 的验证集评估；
- 运行时间、吞吐量、显存峰值和异常日志记录；
- checkpoint 和返回包 SHA-256 计算；
- 完整实验目录私下回传。

B 不得：

- 修改 `.py`、`.yaml`、锁定依赖或固定划分；
- 自行改变学习率、epoch、batch size、阈值、seed 或输出目录；
- 同时叠加任务单未声明的方法；
- 根据一次训练结果自行启动新实验；
- 为排错随意执行 `pip install`、升级包或替换 CUDA/PyTorch；
- 使用测试集训练、分析预测分布、调整参数或生成提交；
- 直接推送或合并 `main`；
- 将数据、权重、checkpoint、特征或预测上传到 GitHub。

命令失败时，B 保留现场、停止任务并回传日志，由 A 判断修复方式。B 不进行猜测性修复。

### 3.3 测试集隔离

两台电脑可能都从官方包得到 `test/`，但权限在流程上必须隔离：

- B 的训练任务只能使用任务单明确给出的训练/验证入口；
- B 不运行 `infer_and_build_submission.py`，不打开历史 `pred_results.csv`；
- A 只有在配置、commit 和 checkpoint 全部锁定后才运行测试推理；
- 任何测试预测统计不得反馈到方法、阈值或类别校正。

### 3.4 训练强度与复赛迁移分工

- A、B 都以提高初赛固定验证和线上 Top-1 为直接目标；初赛结果仍是后续方法价值的主要实证，不因其不计最终综合分而降级。
- B 的算力在未来 3–4 天由两条队列共享：受控的 LoRA rank/alpha/层数粗筛，以及 A 预注册的中强度部分解冻、多随机种子确认和从头复现。LoRA 不做完整笛卡尔积；先单 seed 淘汰，再只复验前列候选。
- A 每个中强度候选必须同时定义两类门禁：初赛 Top-1 晋级门禁，以及复赛可迁移门禁（动态类别数、线性内存复杂度、长尾诊断、无需初赛私有状态）。
- B 仍不得自行把 3 epochs 改成 10 epochs。若学习曲线支持延长，A 必须发布新的配置、commit、资源预算和任务单。
- 已经发给 B 且开始执行的任务不得因策略文档更新而中途换 commit、改配置或停止；新策略从下一份任务单生效，当前结果按实际下发的 commit 和配置验收。
- 复赛数据到位后，两台电脑都不得恢复初赛 checkpoint；A 重新生成当前阶段 manifest/split，B 只执行新阶段任务单。代码可以复用，任何样本级统计必须从复赛训练部分重新计算。

## 4. 训练任务单制度

### 4.1 A 下发任务前

A 必须先完成：

1. 代码和配置提交到 Git；
2. 单元测试和小样本 smoke test；
3. 计算配置哈希；
4. 明确唯一输出目录；
5. 估算运行时间、显存和磁盘增量；
6. 写明成功条件、停止条件和续跑方式；
7. 给 B 一个完整 40 位 commit SHA，不使用“最新代码”作为版本描述。

### 4.2 任务单模板

```text
任务 ID：YYYYMMDD-B-阶段-方法-seed
负责人：A 设计 / B 执行
比赛阶段：preliminary
实验问题：本次只回答一个问题
Git commit：完整 40 位 SHA
要求工作区：clean
配置文件：configs/experiment/xxx.yaml
配置 SHA-256：
数据 manifest SHA-256：
固定 split SHA-256：
上游触发项：
唯一运行命令：
预计高占用时间：
预计 GPU/显存：
预计磁盘增量：
输出目录：artifacts/experiments/<任务ID>/
允许续跑：是/否
续跑命令：
成功条件：
停止条件：
需要返回：完整输出目录、日志、metrics、best/last checkpoint 及哈希
禁止事项：不得改参数、不得读取 test、不得启动任务单外实验
```

任务 ID 必须全局唯一，建议格式：

```text
YYYYMMDD-执行者-阶段-方法-seed
```

例如：`20260912-B-M1-history-seed2`。

### 4.3 B 的标准执行步骤

同步并锁定任务 commit：

```powershell
Set-Location D:\aicomp\AICtrack1
git fetch origin
git switch --detach <任务单中的完整commit>
git rev-parse HEAD
git status --short
```

只有 HEAD 与任务单 SHA 完全相同且工作区干净时才继续。正式训练前运行任务单指定的快速检查，然后原样复制唯一训练命令。

训练开始后：

- 不运行 `git pull` 或切换 commit；
- 不修改配置；
- 不同时启动未声明任务；
- 记录开始时间、GPU 型号、初始显存和命令；
- 只按任务单给出的方式续跑；
- 出现 NaN、CUDA OOM、数据数量不符、读取 test、配置哈希不符或输出目录冲突时立即停止。

### 4.4 B 的完成回报

```text
任务 ID：
实际 commit：
状态：成功 / 中断可续跑 / 失败
开始与结束时间：
总耗时：
峰值显存：
最佳 epoch：
Top-1：
Macro accuracy：
best.pt SHA-256：
last.pt SHA-256：
输出目录：
是否发生异常：
异常日志位置：
```

B 只报告事实，不自行得出“应进入下一阶段”等选模结论。

### 4.5 单机训练互斥与残留锁处理

仓库内自动训练队列统一通过 `src/aictrack1/engine/training_queue.py` 启动训练。守卫同时使用：

1. `artifacts/queues/training.lock.json` 原子文件锁，防止两个队列在检查与启动之间同时穿透；
2. Windows 全系统 Python 命令行探测，发现 `train_peft.py`、`train_frozen_head.py` 或
   `train_final_h1_lora.py` 时拒绝启动；
3. 输出目录完整性检查，只有 metrics、选中 checkpoint、配置和命令全部存在才算已完成。

以下情况一律停机，不等待、不自动跳过、不启动下一项：

- 已有另一个队列持锁；
- 系统内已有训练进程；
- CIM 进程探测失败或返回不可解析结果；
- 输出目录已存在但完成证据不全；
- 子进程异常退出或队列无法确认其已退出；
- 锁文件内容损坏、schema 未知或所有权发生变化。

查看锁状态：

```powershell
.\.venv\Scripts\python.exe scripts\manage_training_lock.py status
```

如果队列被强制结束，锁可能被有意保留。先在任务管理器、`nvidia-smi` 和上述状态输出中确认对应
trainer 已退出，再从最新 `status` 复制完整 token，显式清理：

```powershell
.\.venv\Scripts\python.exe scripts\manage_training_lock.py clear `
  --confirm-stale-token <完整token>
```

清理命令会再次确认队列 owner PID 已退出并探测训练进程；owner 仍在或仍有训练时拒绝删除。不得直接编写“PID 不存在即自动删锁”的逻辑，
也不得删除半成品实验目录。半成品只能由 A 决定续跑、归档或使用新任务 ID 重跑。

## 5. Git 协作规范

### 5.1 分支权限

- `main` 必须始终可运行，由 A 维护和合并；
- A 的功能分支使用 `feat/<stage>-<topic>`、`fix/<topic>` 或 `docs/<topic>`；
- B 默认在 detached HEAD 上执行训练，不需要修改 Git；
- 若 A 明确要求 B 提交轻量运行记录，B 使用 `run/b-<任务ID>` 分支，经 A 审查后合并；
- 两人不得共用一个长期开发分支，不得强制推送共享分支。

建议在 GitHub 为 `main` 开启分支保护：禁止直接推送，要求 Pull Request 和测试通过。A 保留紧急修复权限，但仍应留下可审计 commit。

### 5.2 A 的日常开发流程

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/m2-classwise-clip-trust
# 开发、测试、提交
git push -u origin feat/m2-classwise-clip-trust
```

合并前检查代码、配置、测试、合规、实验假设和 Git 防泄漏。一个 commit 尽量只对应一个可解释改动。

### 5.3 B 的日常同步流程

B 只在当前训练结束或尚未开始时同步：

```powershell
git switch main
git pull --ff-only origin main
```

收到具体任务后再 `git switch --detach <commit>`。B 不得在一次训练中途切换分支、pull 或让代码自动更新。

### 5.4 冲突文件的所有权

以下文件由 A 统一维护，B 不直接编辑：

- `AGENTS.md`；
- `docs/HANDOFF.md`；
- `docs/00_获奖导向总体工作计划.md`；
- `docs/upstream_registry.yaml`；
- `experiments/index.csv`；
- `submissions/ledger.csv`；
- 正式提交相关配置和报告结论。

这样可以避免两人同时追加中央台账导致冲突或结论不一致。

## 6. 实验产物同步规范

### 6.1 GitHub 只保存轻量证据

可进入 Git 的实验记录：

- `config.yaml`；
- `command.txt`；
- `environment.txt` 或 `environment.json`；
- `git_state.txt`；
- `metrics.json`；
- `summary.md`；
- `artifacts_manifest.json`；
- 必要的轻量汇总表和图。

禁止进入 Git：

- `best.pt`、`last.pt`、优化器状态；
- `ViT-B-32.pt`；
- 官方数据和逐样本派生数据；
- 特征缓存；
- 大日志；
- `pred_results.csv` 和提交 ZIP；
- 私有下载信息或凭据。

禁止使用 `git add -f` 绕过 `.gitignore`。

### 6.2 B 向 A 返回训练产物

B 以任务 ID 对应的完整目录为最小传递单位，例如：

```text
artifacts/experiments/20260912-B-M1-history-seed2/
```

返回前确认目录至少包含任务单要求的 config、command、environment、metrics、best/last checkpoint 和哈希。通过 U 盘或团队私有存储传递，不通过公开 GitHub。

A 收到后：

1. 核对任务 ID、commit、配置哈希和数据/split 哈希；
2. 复算 `best.pt`、`last.pt` SHA-256；
3. 检查日志是否存在中断、NaN、OOM、隐式续跑或测试读取；
4. 重新计算或抽查关键验证指标；
5. 将轻量记录复制到 `experiments/<任务ID>/`；
6. 更新 `experiments/index.csv`；
7. 由 A 写继续、停止、复验或排除结论。

当前 `scripts/transfer_workspace.py` 用于首次初始化和灾难恢复，不用于每次训练后的全量双向同步。日常只传新增任务目录，避免反复复制历史数据和 checkpoint。

### 6.3 同名和覆盖规则

- 任务 ID 和输出目录一经下发不得复用；
- 已存在的非空输出目录不得覆盖；
- 失败重跑使用新任务 ID，或严格使用训练器支持的续跑入口；
- A、B 两台电脑上的同名 checkpoint 哈希不同即视为不同产物，停止合并并查明原因；
- 未被 A 验收的 B 产物不得成为新基线或正式提交输入。

## 7. 沟通、故障和安全规则

### 7.1 最小沟通节奏

- A 一次准备 2–4 个按优先级排序、带数值门禁的任务单，减少 B 等待；优先排中强度候选、多种子复现和长尾压力测试，不用无边界网格填满算力；
- B 开始任务时回报任务 ID、commit 和预计完成时间；
- 正常运行不需要频繁报告，只在完成、中断、失败或需要 A 判断时报告；
- A 每日至少一次集中验收结果并发布下一批任务；
- 任何口头参数变更必须由 A 写入新配置并形成新 commit 后才能执行。

### 7.2 B 必须立即停止的情况

- HEAD 或配置哈希与任务单不一致；
- 数据数量、类别数、manifest 或 split 哈希不一致；
- 命令试图读取 `DataSetStage1/test`；
- CUDA OOM、NaN/Inf、损失异常、checkpoint 无法保存；
- 输出目录非空或属于另一任务；
- 依赖缺失、版本不符或需要安装新包；
- 预计时间、显存或磁盘明显超过任务单预算；
- 断电、进程退出或续跑状态不明确。

B 保存完整错误文本、命令和当前目录状态交给 A，不自行删除 checkpoint、清空目录或重置 Git。

### 7.3 凭据和数据安全

- 两人使用各自 GitHub 账号和凭据；
- 不在聊天、仓库或日志中发送密码、token、网盘提取码；
- 官方数据只存放在两台受控开发电脑，不上传公共存储；
- B 不对外转交初始化包或实验产物；
- 离队或设备不再用于比赛时，由队伍负责人确认数据和凭据处理方式。

## 8. 近期并行节奏

当前状态：M0 v2 为严格冻结头基线，M1 单种子 Top-1 为 68.4427%，只领先匹配 M0 v2 约 0.0533 个百分点；必须先确认稳定性，再决定是否进入 M2。

### 阶段一：M1 多种子确认

**A：**

1. 基于当前 M0 v2/M1 配置创建 seed2、seed3 的独立正式配置；
2. 检查除 seed 和输出目录外无额外变量；
3. 完成快速 smoke test；
4. 为 B 发布两个任务单和锁定 commit；
5. 同时准备 M1 聚合分析脚本或表格。

**B：**

1. 顺序执行 M1 seed2、seed3；
2. 不并发挤占单卡显存；
3. 每个任务返回完整目录和哈希；
4. 若一项失败，停止后续相关任务并通知 A。

**门禁：**A 汇总三种子均值、标准差、最差 seed、Top-1 和 macro accuracy。若 M1 提升不稳定，回退 M0 v2 或 M0；稳定增益才将 M1 作为 M2 基线。

### 阶段二：M2 最小实现并行

**A：**

1. 回查 DeFT、CLIPCleaner 及 `docs/05_上游最小复用规格.md`；
2. 只实现一个合规的类内/分块 CLIP 可信度变量；
3. 完成单元测试、资源 smoke 和单种子初筛；
4. 证明不会读取 test、不会引入额外数据或非 OpenAI 权重；
5. 初筛通过后发布 B 的正式长训练任务单。

**B：**

- 等待 A 的锁定任务；
- 可继续执行已批准的 M0/M1 重复性任务；
- M2 未通过 A 的 smoke test 前不自行启动正式训练；
- 收到任务后执行指定 M2 seed，不修改可信度阈值或训练日程。

### 阶段三：M2 验收与 M3 决策

**A：**验收 B 返回产物，完成单变量消融、类别/长尾/冲突样本诊断和多 seed 判断，决定提升、复验或停止。

**B：**执行 A 指定的补充 seed、从头复训或固定资源对照，不参与方法选择。

只有 M2 相对已确认基线获得稳定提升时才进入 M3。禁止为了利用第二台电脑而无门禁地扩大网格搜索。

### 阶段四：锁模与提交

- A 选定最终配置和 checkpoint；
- 必要时 B 执行一次任务单锁定的从头复训，A 验收哈希与指标；
- A 独占测试推理、提交包校验、线上提交和 `submissions/ledger.csv` 更新；
- B 不接收线上分数用于继续调参，只执行 A 在提交前已经预注册的后续训练计划。

## 9. 每日收尾清单

### A

- GitHub `main` 可运行且已推送；
- 新任务均有 commit、配置哈希和任务单；
- 已验收结果进入轻量台账；
- 未验收结果没有被误标为新基线；
- 没有数据、权重、checkpoint 或预测进入 Git；
- 下一批任务的优先级和停止条件明确。

### B

- 当前任务状态已回报；
- 训练目录和 checkpoint 未被覆盖或删除；
- 产物已完成哈希并安全回传；
- 未修改代码、配置、环境或固定划分；
- 未读取测试预测或运行提交脚本；
- 训练结束后再同步下一个指定 commit。

## 10. 原则总结

第二台电脑的价值是提供可靠、可追溯的训练吞吐量，而不是增加未经控制的实验数量。A 负责提出正确问题、实现方法和做决定；B 负责把冻结实验准确运行出来。所有训练必须绑定任务单、commit、配置、数据/split 哈希和唯一输出目录，所有测试推理与正式提交必须集中在 A。
