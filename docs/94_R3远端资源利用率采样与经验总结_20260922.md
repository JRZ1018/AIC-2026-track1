## 1. 结论先行

R3 的 16 个 epoch 已完成，训练主体没有因为资源利用率低而失败。两轮“每秒一次、连续 180 秒”的采样都显示：

- GPU 利用率呈明显突发形态，平均较低、长时间为 0%，但会出现短时高负载；显存远未达到瓶颈。
- 整机 CPU 平均只使用约 12%–13%，但实际启动的 4 个 DataLoader worker 基本各占满一个 CPU 核，说明数据供给并行度偏低。
- 当前没有证据表明需要改变 CLIP、PEFT 结构或损失设计来“填满”L20。后续应把模型结果作为基线保留，另行做数据加载和吞吐优化。

因此，本次先不改模型；资源优化列为后续独立工程任务，避免把运行时调优和算法变量混在同一实验里。

## 5. 经验总结

### 5.1 低 GPU 利用率不等于 GPU 不可用

采样同时出现 0%、50%–70% 和接近 100% 的 GPU SM 利用率，说明 CUDA 计算路径正常，只是每个 batch 之间有明显间隔。只看某一秒的 `nvidia-smi` 容易误判，必须使用连续采样的平均值、分位数和零值比例。

### 5.2 当前作业的主要空闲来自数据管线

显存只占约 3.8%，CPU 总体也很空闲，但已有 worker 各自接近满核；这说明不是模型太大、显存不足或磁盘 iowait 主导，而是 worker 数、预取深度和 epoch 边界生命周期管理限制了供数速度。

### 5.3 DataLoader 生命周期值得单独审计

训练器当前每个 epoch 都重新创建 DataLoader。监控中多次观察到旧 worker 处于退出/等待状态、新 worker 已启动的短暂重叠。它未破坏本次结果，但会增加启动/回收开销，并可能造成 GPU 空等。

### 5.4 算法结果与吞吐要分开评价

R3 的最佳分数由 epoch14 的验证结果决定，epoch16 并未继续提升。后续若只为了提高资源利用率而同时改 batch、worker、学习率或模型结构，就无法判断分数变化来自算法还是运行时。因此，当前 R3 checkpoint 应作为冻结基线保存。

### 5.5 运行环境记录本身也是可靠性的一部分

训练主体已完成，但环境哈希采集因 cuDNN 版本冲突失败，暴露出“训练可跑”与“实验可完整归档”不是同一个门槛。后续正式实验必须在启动前同时检查 CUDA/cuDNN 版本和结束时的 metadata 生成。

## 6. 后续有时间时的改进建议

按优先级排序：

1. **先修环境记录，不重训。** 已将 `capture_environment_identity()` 改为在 cuDNN 版本探测失败时记录明确错误而不是使训练后处理崩溃，并补充回归测试；服务器环境本身仍建议在方便时对齐动态库。R3 历史目录如需补齐 `metrics.json`、`config.yaml` 和 `command.txt`，必须走单独的无训练收尾工具，不能伪造原运行环境。
2. **做独立 DataLoader 吞吐基准。** 保持模型、seed、split、batch 和学习率全部不变，只比较 `workers=4/8/12/16`；增加显式 `prefetch_factor`（建议从 4 开始），观察 samples/s、GPU SM P50/P95 和 epoch wall time。
3. **处理 worker 生命周期。** 优先复用跨 epoch 的 DataLoader，或在重建前显式完成旧 worker 的关闭与垃圾回收，避免旧/新 worker 重叠。该项需配合小规模回归测试，不能直接在正式 R3 结果上热改。
4. **再评估 batch size。** 在 worker 优化后，独立测试 batch 128/256；若改变有效 batch size，必须明确记录学习率、梯度累积和优化语义，不能把吞吐提升实验冒充算法提升实验。
5. **只在证据支持时再做更深层优化。** 若增加 worker 后 GPU 仍长期低于预期，再检查图片解码、变换、缓存和 CPU 亲和性；没有基准数据前不做大范围重构。

## 7. 推荐的后续验证协议

未来开始资源优化时，使用同一 R3 配置复制两个运行：

| 运行 | 算法 | 目的 |
|---|---|---|
| baseline | 当前 `workers=4` | 复现本报告的分数与吞吐 |
| runtime-tuned | 仅改 workers/prefetch/worker 生命周期 | 测量速度和资源利用率，不宣称算法提升 |

两者至少记录：Top-1、macro、tail、最佳 epoch、每 epoch wall time、samples/s、GPU SM 平均/P95/零值比例、CPU user/system/idle、峰值显存，以及完整环境哈希。只有当分数在误差范围内保持一致且 wall time 明显下降时，才把运行时改动合并到正式训练模板。

本报告不解锁新的算法搜索，也不改变复赛合规边界；后续所有训练仍须遵守单模型、单阶段数据、固定 split 和测试集隔离要求。

## 8. 远端 L20 与本机 4060 的实际耗时对照（2026-09-22 补充）

### 8.1 可复核的实测数据

为了避免把不同阶段、不同数据量的数字混在一起，下面分别报告“训练循环本身”的耗时和“整个 epoch 的端到端墙钟耗时”。远端取 R5 两个已完成的 8 epoch AC 短确认（固定 split）；本机取初赛同配方的两个 16 epoch 全量 PEFT 运行。

| 平台/运行 | epoch 数 | 训练样本 | 训练循环平均/epoch | 端到端平均/epoch | 训练样本吞吐 |
|---|---:|---:|---:|---:|---:|
| 远端 L20，seed20260922 | 8 | 118,958 | 326.72 s（5.45 min） | 427.95 s（7.13 min） | 367.75 samples/s |
| 远端 L20，seed20260923 | 8 | 118,958 | 322.42 s（5.37 min） | 423.20 s（7.05 min） | 371.70 samples/s |
| 本机 RTX 4060，初赛 20260918-t | 16 | 103,218 | 286.00 s（4.77 min） | 290.06 s（4.83 min） | 361.21 samples/s |
| 本机 RTX 4060，初赛 20260919-ac | 16 | 103,218 | 281.42 s（4.69 min） | 285.28 s（4.75 min） | 366.94 samples/s |

数据来源：远端 `metrics.json` 的 `history[].train_seconds`、`history[].train_samples_per_second` 与 `duration_seconds`；本机初赛对应实验目录的同名字段。远端两轮的平均值为：训练循环 **324.57 s/epoch（5.41 min）**、端到端 **425.58 s/epoch（7.09 min）**、训练吞吐 **369.72 samples/s**。本机两轮平均为：训练循环 **283.71 s/epoch（4.73 min）**、端到端 **287.67 s/epoch（4.79 min）**、训练吞吐 **364.08 samples/s**。

### 8.2 “提升了多少倍”的正确结论

- 若只看模型训练循环的样本吞吐，L20/4060 实测比为 `369.72 / 364.08 = 1.02×`，即基本持平，L20 只高约 **1.5%**，不能称为 3–5 倍加速。
- 若看从 epoch 开始到 epoch 结束的端到端墙钟时间，远端为本机的 `425.58 / 287.67 = 1.48×`；换成速度，远端只有本机的 **0.676×**，即反而慢约 **32%**。
- 这个端到端差异不能直接归因于 GPU：远端短确认带有 29,737 张固定验证集，本机初赛全量训练没有验证阶段（`validation_count=0`），且 Stage2 训练样本数也比初赛多。因此，最公平的当前比较是“训练循环吞吐”：结论是两者接近，而不是 L20 没有算力。

换句话说，本次作业的“硬件理论优势”大部分被数据读取、DataLoader worker 生命周期、验证阶段和 epoch 间调度开销吃掉了。L20 的低 SM 利用率采样与这一结论相互印证；它不是显存不够，而是没有持续获得足够大的计算批次。

### 8.3 与理论规格的对照

本机实际识别为 GeForce RTX 4060 Laptop GPU；其不同整机 TGP 会造成频率和 FP32 峰值差异，常见规格约为 11.6 TFLOPS FP32、256 GB/s 显存带宽、8 GB 显存。L20 约为 59.8 TFLOPS FP32、864 GB/s、48 GB。以此作数量级比较：

| 指标 | 理论 L20/4060 Laptop 比值 | 本次训练的实测表现 |
|---|---:|---:|
| FP32 峰值 | 约 5.2× | 训练吞吐约 1.02× |
| 显存带宽 | 约 3.4× | 无证据显示带宽成为瓶颈 |
| 显存容量 | 6× | 两边都只使用小部分显存；不是容量瓶颈 |

理论峰值只适用于计算密集、批次足够大且数据供给跟得上的内核；当前末四视觉块 PEFT、batch 64、workers 4 的训练不满足这些条件。因此，“L20 理论上更强”与“本次端到端没有加速”并不矛盾。

### 8.4 对后续训练平台的决策

1. 当前不应为了追求 L20 利用率而改变模型、学习率或 AC 规则；算法结果和运行时优化必须分开。
2. 在本机 4060 可用且服务器按量计费时，本机是更稳妥的默认训练平台；本次实测它的端到端速度更快。
3. 只有在服务器上完成 `workers/prefetch/persistent_workers` 的独立吞吐基准后，才有理由把大规模正式训练迁回 L20。基准必须保持模型、batch、seed、split 和学习率不变，并同时记录 samples/s、每 epoch wall time、GPU SM P50/P95 和 CPU 利用率。
4. 当前远端最终全量 PEFT 在服务器停机前已保存到 `epoch=2` 的恢复 checkpoint，并已回传为 `artifacts/experiments/20260922-stage2-r5-peft-ac-last4-full-16ep-seed20260921/remote_partial_last.pt`；本机 4060 已从该 checkpoint 继续训练。最终全量运行结束后，应把本机实际 epoch 耗时追加到本节，作为同数据量的最终对照。

理论规格参考：NVIDIA L20/HPE QuickSpecs（约 59.8 TFLOPS FP32、864 GB/s、48 GB）与 NVIDIA GeForce RTX 4060 Laptop GPU 规格页；由于 4060 Laptop 的 TGP 可配置，理论值仅作数量级比较，不代替本项目实测。

### 9.1 目标与验收标准

本工作的目标不是单纯把 `nvidia-smi` 数字做高，而是在不改变算法结论的前提下，降低每个有效训练样本和每次完整实验的时间与租金成本。

主要验收指标：

1. 同一模型、数据、split、seed、batch、学习率与 epoch 设置下，训练吞吐至少提高 **50%**，即达到当前基线的 `>= 1.5x`；若低于 20%，不值得为正式管线增加复杂度。
2. 单 epoch 训练墙钟时间至少下降 **30%**。
3. 180 秒连续采样中，GPU SM 平均利用率目标 `>= 40%`，SM 为 0 的采样比例目标 `< 30%`。该指标只作诊断，最终是否合并仍由墙钟时间和成本决定。
4. 固定输入下，训练样本数、采样顺序、数据增强种子、损失定义和 checkpoint provenance 必须保持可复核。
5. 运行时优化不得造成 Top-1、macro、tail 或零召回类数超出既定复现实验容差。仅改变 batch size 的实验不属于纯运行时等价优化，必须单独验分。
6. 最终形成“每百万训练样本成本”“每个完整实验成本”和“相对本机 4060 的实际加速比”，作为是否继续租用 L20 的决策依据。

### 9.2 安全与合规边界

- 不读取 test，不生成新的 test 预测，不消耗提交次数。
- 不覆盖本次正式 R5 目录；所有性能实验使用 `runtime-benchmark-*` 独立 run ID 和输出目录。
- 不在同一个实验里同时修改 workers、prefetch、batch、模型或算法超参数。
- 纯运行时实验保持模型、split、seed、batch、学习率、AC 和 epoch 不变。
- batch size、学习率、梯度累积或并发训练属于独立实验，不能把其结果冒充等价复现。
- 在基准完成前保留当前串行训练守卫；若测试多任务并发，新增显式的受控并发配置，不恢复旧的竞态脚本。

### 9.4 阶段 P1：移除逐 batch CUDA 同步（预计 1–2 小时）

当前训练循环在每个 batch 执行 `float(loss.detach())`、`labels.cpu()` 以及多次 loss/probability/prediction `.cpu()`，会迫使 GPU 与 CPU 频繁同步。

实施内容：

1. 将 loss 累计、类别计数、AC 的样本 loss、观测概率和预测结果留在 GPU 上累计。
2. 在 epoch 结束时只做一次显式同步和一次批量 CPU 回传。
3. 保留非有限 loss 的安全检查；单独测量其同步成本后，再决定每 batch 检查、分段检查或使用异步设备断言。
4. 修正计时：在记录 `train_seconds` 前执行明确的 CUDA 同步，防止异步 kernel 使计时偏小。
5. 添加回归测试，验证样本顺序、loss、置信度状态、类别计数和 checkpoint resume 语义不变。

### 9.6 阶段 P3：真正复用 DataLoader worker（预计 2–4 小时）

当前虽设置 `persistent_workers=True`，但 DataLoader 在每个 epoch 内重建，worker 并未真正跨 epoch 常驻。

实施内容：

1. 将训练和验证 DataLoader 生命周期移到 epoch 循环外。
2. 为数据集增加 worker 可见的 epoch 状态，确保 `set_epoch()` 能传播到持久 worker。
3. 保持当前按 `seed + epoch + sample_index` 定义的数据增强可复现性。
4. 为自然采样、WeightedRandomSampler、断点续训分别增加顺序和状态恢复测试。
5. 检查 epoch 边界不再出现旧/新 worker 重叠和重复解码预热。

### 9.7 阶段 P4：CPU 图像解码与变换优化（预计 2–4 小时）

按低风险到高风险顺序处理：

1. 去掉 `Image.open(...).convert("RGB")`、transform 和 `_normalize()` 之间的重复 RGB 转换。
2. 将 CLIP mean/std Tensor 预先构造并复用，避免每张图片重新分配。
3. 基准 Pillow/libjpeg-turbo 或 torchvision v2 的 JPEG 解码与 resize/crop。
4. 若 CPU 解码仍是主瓶颈，再评估把仅含 train 的图片预先转换为适合顺序读取的缓存格式，或使用 DALI/nvJPEG。
5. 缓存方案必须保留原始图片与 manifest 哈希关系，不能改变数据内容或跳过坏图审计。

验收：随机抽样对比变换输出尺寸、范围、归一化、随机种子和标签完全符合原管线契约。

### 9.8 阶段 P5：batch size 与显存利用实验（预计 1–2 小时）

在完成等价运行时优化后，再单独测试 batch 128、256；显存允许时可探测 512，但不预设其有效。

注意：batch size 会改变优化动力学，因此此阶段属于算法重新确认，不是等价运行时优化。每次只改 batch，并明确处理学习率、scheduler 和有效 batch 语义。必须观察 Top-1、macro、tail、有效训练质量和零召回类，不能只看速度。

若 batch 增大带来吞吐提升但精度下降，则不进入正式配置；可以仅用于不要求与正式训练完全同构的早期吞吐筛选。

固定 workers=16、prefetch=4 和其他全部算法参数，对 batch 64/128/256 各运行 2 epochs。
实验目标是“单位时间获得更高验证分数”，不是填满 48 GiB 显存。

|---:|---:|---:|---:|---:|---:|---:|---:|

| 128 | 1143.44 samples/s | 283.41 s | 1633.3 MiB | 0.658405 | 0.650275 | 0.652433 | 7 |
| 256 | 1198.78 samples/s | 272.48 s | 2627.5 MiB | 0.656018 | 0.648046 | 0.651884 | 7 |

### 9.9 阶段 P6：多实验受控并发与租金利用率（预计 2–3 小时）

该阶段只用于同时存在多个独立候选实验时，不能用于单一最终模型。

负责人于 2026-09-23 确认：后续 L20 候选筛选应记得优先安排“两个相互独立的 batch-64
候选实验”受控并行，目标是更快产出可比的验证分数，不是填满显存。这是后续执行约定，仍需先
完成并发队列的锁、输出隔离和故障退出实现与短基准，不允许直接绕过现有串行守卫。

1. 新增显式 `max_concurrent_jobs=2` 的队列模式，禁止无界并发。
2. 每个任务分配独立日志、run ID、锁和退出码，失败不能影响其他任务。
3. 先测试 2 个任务并行，再根据显存、CPU、单任务吞吐和总吞吐决定是否测试 3–4 个任务。
4. 比较指标是“单位墙钟时间完成的训练样本/实验数”和“每个成功实验成本”，不是单进程 GPU 利用率。
5. 如果并发使单任务明显变慢但总吞吐提高，仍可用于超参数筛选；最终训练继续单任务运行。

### 9.10 决策门槛与服务器选型

- 若 L20 单任务吞吐达到本机 `>= 2x`，且成本可接受：继续把重训练放在 L20。
- 若达到 `1.5x–2x`：根据抢占式价格、稳定性和是否需要并发实验决定。

- 若优化需要改变算法或牺牲精度才能获得速度，则不作为默认正式训练配置。

- 显存控制器平均仅 18.26%，仍不支持“L20 受显存带宽限制”的判断。

这证明增加 DataLoader 并行度和预取深度确实改善了 GPU 获得 batch 的连续性，但尚未达到专项
目标（SM 平均 ≥40%、零值 <30%）。是否值得继续做 P2/P3，仍应以完整 epoch 墙钟和每百万样本
成本为主，不以单次 `nvidia-smi` 数字作为合并理由。

### 10.4 当前调度决策

此前双任务 2-epoch 门禁中，每个任务均正常完成，但总墙钟约 550 秒，而同配置单任务约 297 秒；
双任务总吞吐约为单任务的 0.54 倍。因此，本批 A1/A2 改为单锁串行执行。三分钟采样进一步说明：
单任务 `workers=16、prefetch=4` 已能让 L20 的计算窗口明显连续，继续并发会增加 CPU/DataLoader
竞争，不能以“显存还空着”为理由强行并发。

后续若继续资源优化，优先级保持：

1. 先以 A2/A1 完整 epoch wall time、samples/s 和成本为基线；
2. 再单变量验证 P2 的逐 batch CUDA 同步减少，必须保持 AC 状态和 checkpoint 数值等价；
3. 只有 P2 无效时才进入持久 DataLoader worker 生命周期改造；
4. 不因为显存低利用率而修改 batch、学习率、模型或 AC，算法提分与运行时优化继续分开。
